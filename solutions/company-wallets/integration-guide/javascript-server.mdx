## Overview

It exposes a ready-made API client class which manages the process of constructing requests to the
Turnkey API and authenticating them with a valid API key. Furthermore, it exposes API proxies that
forward requests from your application's client that need to be signed by parent organizations API
key.

Use the [`@turnkey/sdk-server`](https://www.npmjs.com/package/@turnkey/sdk-server) package to handle
server-side interactions for applications that interact with the Turnkey API.

## Installation

<CodeGroup>

## Initializing

```js
import { Turnkey } from "@turnkey/sdk-server";

const turnkey = new Turnkey({
  defaultOrganizationId: process.env.TURNKEY_ORGANIZATION_ID,
  apiBaseUrl: "https://api.turnkey.com",
  apiPrivateKey: process.env.TURNKEY_API_PRIVATE_KEY,
  apiPublicKey: process.env.TURNKEY_API_PUBLIC_KEY,
});
```

## Creating clients

Calls to Turnkey's API must be signed with a valid credential (often referred to in the docs as
[stamping](/api-reference/overview/stamps)) from the user initiating the API call. When
using the Server SDK, the user initiating the API call is normally your root organization, and the
API call is authenticated with the API keypair you create on the Turnkey dashboard.

#### `apiClient()`

The `apiClient` method returns an instance of the `TurnkeyApiClient` which will sign requests with
the injected `apiPrivateKey`, and `apiPublicKey` credentials.

```js
const apiClient = turnkey.apiClient();
const walletsResponse = await apiClient.getWallets();

// this will sign the request with the configured api credentials
```

## Creating API proxies

For parent-initiated authentication, your backend signs the initialization, encrypted verification, and login requests with its parent-organization API key. You can implement dedicated routes with `apiClient()` or expose an explicit set of methods through a proxy handler.

Use `@turnkey/sdk-server` 6.0.0 or later for encrypted OTP support. Upgrade the client packages and update policies before deployment; see the [OTP migration guide](/features/authentication/otp-migration-guide).

The examples below allow existing-user OTP login. They do not grant signup or account-lookup access. A method allowlist is not application authentication or input validation: enforce your application's authorization and rate limits before forwarding requests. Keep parent API keys on the backend and plaintext OTP codes on the client.

`otpLogin` must target the user's sub-organization, so the client needs that ID before it calls the proxy. Return it from a dedicated backend route that resolves the sub-organization only for the contact proven by the verification token; see [Verify the encrypted code](#verify-the-encrypted-code). Do not add `getSubOrgIds` to the allowlist: a proxied lookup lets any caller check whether an email address or phone number has an account.

#### expressProxyHandler()

The `expressProxyHandler()` method creates a proxy handler designed as a middleware for Express
applications. It provides an API endpoint that forwards requests to the Turnkey API server.

```js
const turnkeyProxyHandler = turnkey.expressProxyHandler({
  allowedMethods: ["initOtp", "verifyOtp", "otpLogin"],
});

app.post("/apiProxy", turnkeyProxyHandler);

// this will sign requests made with the client-side `serverSign` function with the root organization's API key for the allowedMethods in the config
```

#### nextProxyHandler()

The `nextProxyHandler()` method creates a proxy handler designed as a middleware for Next.js
applications. It provides an API endpoint that forwards requests to the Turnkey API server.

```js
// Configure the Next.js handler with allowed methods
const turnkeyProxyHandler = turnkey.nextProxyHandler({
  allowedMethods: ["initOtp", "verifyOtp", "otpLogin"],
});

export default turnkeyProxyHandler;

// this will sign requests made with the client-side `serverSign` function with the root organization's API key for the allowedMethods in the config
```

## Email and SMS authentication

Use the following sequence for a custom backend. These are excerpts from separate request handlers, not one server-side function: initialization returns to the client, verification follows client-side encryption, and login follows client-side signing. The `turnkey` instance is initialized on the server as shown above.

### Initialize an attempt

Submit `ACTIVITY_TYPE_INIT_OTP_V3` through `initOtp` under the parent organization:

```ts
const { otpId, otpEncryptionTargetBundle } = await turnkey.apiClient().initOtp({
  otpType: "OTP_TYPE_EMAIL", // Use OTP_TYPE_SMS for SMS.
  contact,
  appName: "Example App",
});
```

Return both values to the client. The client generates or selects a P-256 key and encrypts the OTP code and public key with the returned bundle. The private key and plaintext code stay on the client. Keep the ID, bundle, and client key together for the same attempt; replace attempt state on resend.

See [client-side encryption and signing](/features/authentication/otp-migration-guide#replace-initialization-verification-and-login) for the client implementation. For the full request fields, see [Init generic OTP](/api-reference/activities/init-generic-otp).

### Verify the encrypted code

Receive `otpId` and `encryptedOtpBundle` from the client. Use the same organization as initialization:

```ts
const { verificationToken } = await turnkey.apiClient().verifyOtp({
  otpId,
  encryptedOtpBundle,
});
```

This submits `ACTIVITY_TYPE_VERIFY_OTP_V2`. Return the verification token to the client so it can sign the login request with the key bound during verification. Do not accept a plaintext `otpCode` in the backend request or encrypt it on the server.

Resolve the existing user's sub-organization after verification, using the verified contact and [Get sub-org IDs](/api-reference/queries/get-sub-organizations). For new users, follow [OTP signup](#otp-signup).

### Create a session

Receive `verificationToken`, the session `publicKey`, and `clientSignature` from the client. The client must construct the protocol's login message and sign it with the private key bound during verification; signing the raw token or arbitrary JSON is not equivalent.

```ts
const { session } = await turnkey.apiClient().otpLogin({
  organizationId: subOrgId,
  verificationToken,
  publicKey,
  clientSignature,
  expirationSeconds: "900",
});
```

This submits `ACTIVITY_TYPE_OTP_LOGIN_V2`. Return `session` to the client and store it using that SDK's session API, retaining the matching client-held private key. See [Login with OTP](/api-reference/activities/login-with-otp) for the client signature fields and optional session settings.

Initialization, verification, and login have separate expiration settings. `expirationSeconds` on login sets the session lifetime. If you set `invalidateExisting: true`, it invalidates the user's other login sessions, including sessions created through other login methods.

### OTP signup

If no existing account matches the verified contact, create a sub-organization with `ACTIVITY_TYPE_CREATE_SUB_ORGANIZATION_V8` or a later supported version. Pass the enclave-issued `verificationToken` and a signup `clientSignature` generated by the verification-bound key. A login signature cannot be reused for signup. See [Create sub-organization](/api-reference/activities/create-sub-organization) and the [complete backend example](https://github.com/tkhq/sdk/tree/main/examples/authentication/otp-auth/with-backend).

### Recovery

Use encrypted OTP authentication and an appropriately restricted recovery session to enroll a replacement authenticator. Preserve MFA requirements and confirm that the replacement authenticator works before completing recovery. See [Replace email recovery](/features/authentication/otp-migration-guide#replace-email-recovery).

## Social authentication

For providers that issue OIDC ID tokens directly, use [Login with OAuth](/api-reference/activities/login-with-oauth). Bind the provider token's nonce to the client-held session key as described in [Social logins](/features/authentication/social-logins#oidc-provider).

Providers such as X and Discord require a separate OAuth 2.0 exchange before login. Follow the [OAuth 2.0-only provider guidance](/features/authentication/social-logins#oauth-2-0-only-provider).

### Create an OAuth session

Receive the provider's `oidcToken` and the session `publicKey` from the client. The client sets the OAuth request's `nonce` to `sha256(publicKey)`, which binds the resulting token to its key pair. Resolve the user's sub-organization with [Get sub-org IDs](/api-reference/queries/get-sub-organizations), filtered by `OIDC_TOKEN`, then submit `ACTIVITY_TYPE_OAUTH_LOGIN` through `oauthLogin`:

```ts
const { session } = await turnkey.apiClient().oauthLogin({
  organizationId: subOrgId,
  oidcToken,
  publicKey,
  expirationSeconds: "900",
});
```

Turnkey checks that the token's `nonce` matches `sha256(publicKey)` before returning the session JWT. Return `session` to the client and store it using that SDK's session API, retaining the matching client-held private key. See [Login with OAuth](/api-reference/activities/login-with-oauth) for optional fields such as `invalidateExisting` and `sessionProfileId`.
