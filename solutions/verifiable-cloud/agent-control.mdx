An agent can be useful long before it is safe to trust with production changes, money movement, or sensitive data. The common fixes are expensive and brittle: require a person to approve every step, give the agent a broad credential and review logs later, or build a custom proxy whose operator can silently change its rules.

TVC provides a narrower option. Keep the general-purpose agent in its existing runtime, but put the consequential decision path behind a small application whose code, configuration, and approvals can be verified.

## The workflow

1. The agent proposes a typed action, such as a transaction or configuration change.
2. A TVC application validates the request against deterministic business rules and any required Turnkey policy outcome.
3. The application returns an allow or deny decision in a purpose-built App Proof payload.
4. The system that can perform the action verifies the App Proof, its linked Boot Proof, and the expected application digest before proceeding.

The result is a verifiable control point. Reviewers can inspect the exact decision program rather than trusting a dashboard log generated by the same service being audited.

## Business outcome

- Automate repetitive approvals without turning off controls entirely.
- Make a compromised agent less useful to an attacker by keeping final authority behind a separate policy boundary.
- Give security teams and counterparties independently checkable evidence for the specific decision they care about.
- Change production rules through the same reviewed deployment process as code, with cryptographic manifest approvals.

## Why TVC fits

| Need | TVC building block |
| :--- | :--- |
| Identify the exact control code | The Boot Proof binds the enclave's Ephemeral Key to the QOS manifest and application binary digest. |
| Prove which code produced a decision | The application signs its typed decision payload with the per-boot Ephemeral Key. |
| Prevent one administrator from changing the control path | A manifest set can require multiple operators to approve each deployment. |
| Keep a stable application identity across approved upgrades | The Quorum Key persists separately from the per-boot Ephemeral Key and can protect long-lived application state. |
| Require identity- and action-specific authorization | Turnkey policies evaluate requests inside Turnkey's secure enclaves before protected operations execute. |

## What you build

TVC runs the application you supply; it is not a complete agent runtime or tool-permission product. Your application defines:

- the request schema and deterministic checks;
- the App Proof schema and which request and result fields it commits to;
- the verifier's accepted application digests and deployment policy; and
- the downstream rule that refuses unverified or denied actions.

Keep the TVC application small. Stateful conversations, model routing, general tool execution, and user interfaces can remain outside the enclave unless they are part of the claim a verifier must check.

## Proof boundaries

This pattern proves that identified code signed a particular decision. It does not prove that a model provider ran a named model, that every event in an agent session was recorded, or that the agent never observed other data. Those require separate evidence and should not be inferred from an App Proof.
