## Overview

Use this guide if you want to run authentication through your own server instead of Turnkey's Auth Proxy. Your backend will call Turnkey's public API for OTP, OAuth, and signup. The Swift SDK will:

- Generate and protect the on-device API key pair
- Create or resume sessions
- Persist and expose session/user/wallet state via `TurnkeyContext`

If you prefer a no-backend setup, use the [Auth Proxy](/features/authentication/auth-proxy) instead.

## What you can't use

The following high-level helpers on `TurnkeyContext` are designed for the Auth Proxy and will throw `missingAuthProxyConfiguration` when the proxy is disabled:

- `initOtp`, `verifyOtp`, `completeOtp`
- `handleGoogleOAuth`, `handleAppleOAuth`, `handleDiscordOAuth`, `handleXOauth`
- `signUpWithPasskey`

For a backend flow, your app talks to your server for OTP/OAuth/signup and only stores the resulting session locally.

## Disable the Auth Proxy

Omit `authProxyConfigId` when configuring the SDK:

```swift
import TurnkeySwift

TurnkeyContext.configure(TurnkeyConfig(
  organizationId: "<your_org_id>",
  rpId: "<your_app_domain>" // required for passkeys
  // Do not set authProxyConfigId when using your own backend
))
```

With the proxy disabled, `TurnkeyContext.client` will be stamper-only after you create/store a session.

## On your backend

Implement endpoints that forward to Turnkey's public API. Depending on your flow, you'll typically use:

- [`createSubOrganization`](/api-reference/activities/create-sub-organization) — signup
- [Init generic OTP](/api-reference/activities/init-generic-otp) — `ACTIVITY_TYPE_INIT_OTP_V3`
- [Verify generic OTP](/api-reference/activities/verify-generic-otp) — `ACTIVITY_TYPE_VERIFY_OTP_V2`
- [Login with OTP](/api-reference/activities/login-with-otp) — `ACTIVITY_TYPE_OTP_LOGIN_V2`
- [Login with OAuth](/api-reference/activities/login-with-oauth) — for an OIDC token bound to the client key

Notes:

- Passkey and external wallet login happen on-device via [`login-with-a-stamp`](/api-reference/activities/login-with-a-stamp). Signup still requires `createSubOrganization` on your backend.
- You may apply custom validation, logging, and rate limiting in your server.

For a TypeScript backend, use `@turnkey/sdk-server` 6.0.0 or later and the [encrypted OTP server flow](/solutions/company-wallets/integration-guide/javascript-server#email-and-sms-authentication). Turnkey also provides [Rust](https://github.com/tkhq/rust-sdk) and [Go](https://github.com/tkhq/go-sdk) SDKs. Whichever language you use, the activity versions and client/server boundary below are the same.

### OTP signup

An email address in `rootUsers` does not prove ownership of that address. Complete encrypted OTP verification first, then submit `ACTIVITY_TYPE_CREATE_SUB_ORGANIZATION_V8` or a later supported version with the `verificationToken` and a signup `clientSignature` made by the verification-bound client key. Include the intended root users and credentials as described in [Create sub-organization](/api-reference/activities/create-sub-organization).

Use the signup message format for the selected activity version; do not reuse a login signature. Keep the root-user configuration and the signed signup payload consistent. See the [OTP migration guide](/features/authentication/otp-migration-guide) for policy and SDK requirements.

## On your iOS app

In your iOS app, you will need to implement your own authentication flows that interact with your backend endpoints.

### Create a key pair

Login endpoints like `otpLogin` and `oauthLogin` will require a public key to be passed in the request.

You can use `createKeyPair` from the `TurnkeyContext` to generate a keypair for this purpose.

```swift
import SwiftUI
import TurnkeySwift

struct CreateKeyPairExample: View {
  @EnvironmentObject private var turnkey: TurnkeyContext

  func createPublicKey() throws -> String {
    try turnkey.createKeyPair()
  }
}
```

The private key will be generated in the Secure Enclave if available, otherwise it will be generated then securely stored within the Keychain. The public key will be returned and can be passed to your backend.

### Store the session returned by your backend

Your backend will return a session JWT. Store it locally so the SDK can manage future stamps automatically:

```swift
import SwiftUI
import TurnkeySwift

struct StoreSessionExample: View {
  @EnvironmentObject private var turnkey: TurnkeyContext

  func store(sessionToken: String) async throws {
    try await turnkey.storeSession(jwt: sessionToken)
  }
}
```

After that, `TurnkeyContext.shared.client` is ready for signed API calls, and `authState` will be `.authenticated`.

If you have `autoRefreshSession` enabled under the auth object in the `TurnkeyConfig` configuration, the SDK will automatically refresh the session token when it expires.
You can also use the `authState` variable from the `TurnkeyContext` to check if the user is authenticated.

```swift
import SwiftUI
import TurnkeySwift

struct ContentView: View {
  @EnvironmentObject private var turnkey: TurnkeyContext

  var body: some View {
    Group {
      switch turnkey.authState {
      case .authenticated:
        Text("Welcome back!")
      case .loading:
        ProgressView()
      default:
        Text("Please log in")
      }
    }
  }
}
```

### OTP login protocol

The app must encrypt the code before it leaves the device and sign the login message with the key bound during verification. The table describes the application backend contract; route names are chosen by your application.

| Step | iOS app | Backend |
| --- | --- | --- |
| Initialize | Request an OTP for the user's contact. | Submit `INIT_OTP_V3` under the parent organization with `otpType`, `contact`, and `appName`. Return both `otpId` and `otpEncryptionTargetBundle`. |
| Encrypt | Generate or select a P-256 key. Use the returned target bundle to encrypt the OTP code and public key on-device. Send `otpId` and `encryptedOtpBundle`. | Receive the encrypted bundle; never require the plaintext code or client private key. |
| Verify | Retain the key for this attempt. | Submit `VERIFY_OTP_V2` under the same organization as initialization. Return the `verificationToken` to the app and resolve the existing sub-organization for the verified contact. |
| Sign | Construct the protocol's login message from the verification token and session key, then sign it with the verification-bound private key. Send `verificationToken`, the session `publicKey`, and `clientSignature`. | Submit `OTP_LOGIN_V2` to the resolved sub-organization with those fields. Return its `session` JWT. |
| Store | Call `storeSession(jwt:)` with the returned JWT. Retain the private key matching the session public key. | — |

The parent organization's API key stays on the backend for every step.

`clientSignature` contains `scheme`, `publicKey`, `message`, and `signature`; see [Login with OTP](/api-reference/activities/login-with-otp). Use SDK encryption and signing helpers that implement the encrypted OTP protocol. Signing the raw verification token or an arbitrary JSON object does not produce the required login message. The [OTP migration guide](/features/authentication/otp-migration-guide#replace-initialization-verification-and-login) describes the message construction and client/server sequence.

Do not move encryption or client signing to the backend to work around a missing helper. If your Swift SDK integration cannot yet implement this protocol, use the supported [Auth Proxy email/SMS flow](/solutions/embedded-wallets/integration-guide/swift/authentication/email-sms) rather than a plaintext backend flow.

Keep `otpId`, `otpEncryptionTargetBundle`, and the client key as state for one attempt. On resend, discard the previous attempt state. Surface verification and login errors to the user, and only store a session after login succeeds.

For account recovery, follow [Replace email recovery](/features/authentication/otp-migration-guide#replace-email-recovery), including restricted session permissions, MFA, and replacement authenticator enrollment.
