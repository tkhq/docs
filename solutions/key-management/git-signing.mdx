Coding agents commit, push, and clone. To do this today, they usually use your signing key and your SSH key, which sit in `~/.ssh` or a GnuPG keyring that the agent can read and copy. Its commits then look like yours, and you cannot revoke its access without rotating your own keys.

With the [`tk` CLI](https://github.com/tkhq/tk), an agent signs Git commits and opens SSH connections without a private key on its machine. Turnkey holds the key, evaluates a [policy](/features/policies/overview) on every signature, and logs every approval.

- **Git signing**: `tk` acts as Git's GPG or SSH signing program, so `git commit -S` and `git verify-commit` work unchanged.
- **SSH**: `tk ssh agent` serves Turnkey keys on a standard `SSH_AUTH_SOCK`, so `ssh`, `git push`, and `git clone` over SSH work unchanged.

This page is written for agents, but the same setup works for a person who wants to sign their own commits. See [Sign your own commits](#sign-your-own-commits).

## Why Turnkey for Git signing and SSH?

For an agent on your laptop, such as Claude Code or Codex in a terminal:

- **No key for the agent to read**: the signing and SSH keys stay in Turnkey, not in a file or keyring that the agent can read or copy.
- **Its own identity**: the agent signs and connects with its own key, not yours. Its commits are attributable, and you can revoke its access without touching your keys.
- **Policy and audit**: Turnkey policies decide which keys the agent can use, and Turnkey logs every signature.

For an unattended agent in CI, a container, or a VM:

- **Expiring session keys**: the agent generates its own API key, and a separate provisioner registers it with an expiry and renews it.
- **Signing broker**: a separate process holds the signing credential. The agent gets only a Unix socket and a public key.
- **Policy-scoped signing**: each agent can sign only with the keys that a policy names. When you delete its API key, it cannot sign again.

## How it works

Git calls a signing program for each signed commit or tag. You set that program to `tk`. `tk` sends the payload to Turnkey as a sign request, authenticated with the agent's API key. The [policy engine](/features/policies/overview) evaluates the request inside the [secure enclave](/security/secure-enclaves). If a policy allows it, Turnkey returns the signature, and `tk` gives it to Git in the format that Git expects.

SSH works the same way. `tk ssh agent` listens on a Unix socket and speaks the standard SSH agent protocol. When `ssh` or `git push` asks it to sign a login challenge, it sends the challenge to Turnkey.

| Part | What it is |
| :--- | :--- |
| **Agent user** | A non-root Turnkey user with the `agent` tag. Its API key is the only credential on the agent's machine. |
| **Signing key** | An OpenPGP key backed by an account in a wallet, or a Turnkey Ed25519 private key for SSH signing. |
| **SSH key** | A Turnkey Ed25519 private key that `tk ssh agent` serves for `ssh` and `git push`. |
| **Policies** | One ALLOW policy for each key. It names the agent user and the exact wallet or private key. A DENY policy stops agents from changing their own credentials. |
| **`tk` profile** | A named local profile that holds the agent's API key. Git's signing program uses this profile. |

Turnkey denies all requests by default. An agent user that no policy names cannot sign with any key.

## Key implementation decisions

| Decision | What to consider | Learn more |
| :--- | :--- | :--- |
| **Signature format** | GPG and SSH signatures both show as Verified on GitHub. With GPG, the agent can use one Ed25519 key for SSH and a separate key for signing. With SSH signing, one key can do both. | [tk Git signing](https://github.com/tkhq/tk/blob/main/docs/git-signing.md) |
| **Committer identity** | Use your name with `(agent)` and your email address with a plus tag, such as `Jane Doe (agent) <jane+agent@example.com>`. Its commits group with yours in `git shortlog`, and GitHub sends the email confirmation link to your inbox. | [Committer identity](https://github.com/tkhq/tk/blob/main/docs/git-signing.md#committer-identity) |
| **Where the Git config lives** | If you sign with your own key on the same machine, put the agent's Git config in the agent runtime's environment, not in `~/.gitconfig`. | Step 4 of [Set up by hand](#set-up-by-hand) |
| **Approval** | Git waits for each signature, so the signing policy must allow the agent to sign without an approval step. Limit what the agent can sign with the policy condition, not with a human approval. | [Policy language](/features/policies/language) |
| **SSH destinations** | A Turnkey policy cannot see which host an SSH challenge is for. To limit the hosts, start `tk ssh agent` with an allowed-hosts file. | [Destination constraints](https://github.com/tkhq/tk/blob/main/docs/ssh-agent.md#destination-constraints) |
| **Revocation** | Delete the agent user's API key to stop all signing and SSH at once. Delete one policy to stop the use of one key. | [Users](/features/users/introduction) |

## Set up with your agent

The `tk` binary contains a set of agent skills. The `signing-git-commits` and `using-ssh` skills do the steps on this page. Paste this into your agent:

```
Install the Turnkey tk CLI with
`curl --proto '=https' --tlsv1.2 -LsSf https://raw.githubusercontent.com/tkhq/tk/main/install.sh | sh`.
Install the tk skills with `tk skills install --into <your skills directory>`,
read the installed turnkey-tk/SKILL.md, and walk me through bootstrapping my
Turnkey organization at https://app.turnkey.com. Then give yourself your own
agent identity, sign your Git commits with a Turnkey key, and push over SSH
with a Turnkey key.
```

The agent does the root steps with your admin profile and tells you when it needs you. You do the steps in the dashboard and on GitHub.

## Set up by hand

<Note>
  This setup is for a local agent that runs as your OS user, with the same `HOME`. For agents in CI, containers, or VMs, see [Background agents](#background-agents).
</Note>

<Steps>
  <Step title="1. Install tk and save a root profile">
    Install `tk`:

    ```bash
    curl --proto '=https' --tlsv1.2 -LsSf https://raw.githubusercontent.com/tkhq/tk/main/install.sh | sh
    tk --version
    ```

    The installer puts `tk` in `~/.local/bin`. If `tk --version` says `command not found`, add that directory to your `PATH` and open a new shell: `export PATH="$HOME/.local/bin:$PATH"`. Add the same line to your shell profile (`~/.zshrc` on macOS, `~/.bashrc` and `~/.profile` on Linux). If your agent runs commands in a shell that does not read that file, call `~/.local/bin/tk` by its full path.

    Make sure that `tk --version` shows the version on the [tk releases page](https://github.com/tkhq/tk/releases/latest). If the download fails, the pipe can still exit 0, and an older `tk` on your `PATH` can answer instead.

    Create a profile for your root user. `tk` generates an API key and prints its public key. In the [Turnkey Dashboard](https://app.turnkey.com), open your user, add an API key, open **Advanced settings**, and paste the public key (curve P-256).

    ```bash
    tk --organization-id ORG_UUID profile create --profile-name admin
    tk login --profile-name admin
    tk --profile admin whoami
    ```

    If you have a root API key file already, add `--api-key-file /full/path/to/root-key.json` to `profile create`. `tk` then uses that key and does not generate a new one. The profile points to that file and does not copy it, so keep the file where it is. If the key is already on your root user, do not add it in the dashboard again. Still run `profile create` with `--api-key-file`, because `tk login` needs the profile. `profile create` prints a message that tells you to register the public key. Ignore it, and run `tk login`.
  </Step>

  <Step title="2. Create the agent identity">
    The steps keep IDs in shell variables, such as `AGENT_TAG`, `AGENT_USER_ID`, `WALLET_ID`, and `FINGERPRINT`. If your agent runs each command in a new shell, it loses the variables. Write each value to a file, for example `echo "AGENT_USER_ID=$AGENT_USER_ID" >> ~/.config/turnkey/setup.env`, and run `. ~/.config/turnkey/setup.env` at the start of each later command.

    Create the `agent` tag, if your organization does not have it:

    ```bash
    tk --profile admin user tag list
    tk --profile admin user tag create --name agent
    ```

    Save the ID of the `agent` tag as `AGENT_TAG`. It is in the `user tag list` output, or you can read it with `jq`:

    ```bash
    AGENT_TAG=$(tk --profile admin --message-format json user tag list \
      | jq -r '.data.userTags[] | select(.tagName=="agent") | .tagId')
    ```

    Generate the agent's API key on the machine where the agent runs. Save the public key as `PUBLIC_KEY`:

    ```bash
    PUBLIC_KEY=$(tk --organization-id ORG_UUID --message-format json profile create --profile-name agent \
      | jq -r .data.publicKey)
    ```

    `profile create` prints a message that tells you to register the public key. The next command, `user create`, does this.

    Create the agent user with that public key. Save the user ID from the result as `AGENT_USER_ID`:

    ```bash
    AGENT_USER_ID=$(tk --profile admin --message-format json user create \
      --user-name agent --tag-name agent --public-key "$PUBLIC_KEY" \
      | jq -r '.data.activity.result.createUsersResult.userIds[0]')
    ```

    Stop all agents from changing credentials. This policy is for all agents in the organization, so look for it first:

    ```bash
    tk --profile admin policy list
    ```

    If `agents-no-credentials` exists, make sure that its consensus has this tag ID and its condition is `activity.resource == 'CREDENTIAL'`, and do not create it again. If it does not exist, create it:

    ```bash
    tk --profile admin policy create --name agents-no-credentials --effect deny \
      --consensus "approvers.any(user, user.tags.contains('${AGENT_TAG}'))" \
      --condition "activity.resource == 'CREDENTIAL'"
    ```

    Log in as the agent and make sure that `whoami` shows `AGENT_USER_ID`:

    ```bash
    tk login --profile-name agent
    tk --profile agent whoami
    ```

    `tk login` also selects `agent` as the default profile. Pass `--profile admin` or `--profile agent` in every command, or run `tk login --profile-name admin` to select your root profile again.
  </Step>

  <Step title="3. Create the signing key">
    <Tabs>
      <Tab title="GPG">
        Create an empty wallet for the signing key:

        ```bash
        WALLET_ID=$(tk --profile admin --message-format json wallet create \
          --input-json '{"walletName":"git-signing","accounts":[]}' \
          | jq -r .data.activity.result.createWalletResult.walletId)
        ```

        Let the agent sign with that wallet, and nothing else:

        ```bash
        tk --profile admin policy create --name agents-sign-gpg --effect allow \
          --consensus "approvers.any(user, user.id == '${AGENT_USER_ID}')" \
          --condition "activity.type == 'ACTIVITY_TYPE_SIGN_RAW_PAYLOAD_V2' && wallet.id == '${WALLET_ID}'"
        ```

        Create the OpenPGP key. The user ID is the agent's committer identity:

        ```bash
        FINGERPRINT=$(tk --profile admin --message-format json gpg keys create \
          --wallet-id "$WALLET_ID" --user-id 'Jane Doe (agent) <jane+agent@example.com>' \
          | jq -r .fingerprint)
        ```

        As the agent, register the key and import the public key into a GnuPG home of its own. This keeps your keyring unchanged. If the export succeeds, the policy works:

        ```bash
        tk --profile agent gpg keys add --wallet-id "$WALLET_ID" --key "$FINGERPRINT"
        export GNUPGHOME="$HOME/.config/turnkey/tk/gnupg"
        mkdir -p "$GNUPGHOME" && chmod 700 "$GNUPGHOME"
        tk --profile agent gpg keys export --key "$FINGERPRINT" | gpg --import
        echo "$FINGERPRINT:6:" | gpg --import-ownertrust
        unset GNUPGHOME
        ```

        If the export fails with `unauthorized` (403), check the agent user ID and the wallet ID in `agents-sign-gpg`. If it fails with 429, the organization is over its rate limit. Wait a few minutes, then run the `export`, `gpg --import`, and `--import-ownertrust` commands again with the same `GNUPGHOME`. Make sure that `gpg --list-keys` shows the agent's key before you run `unset GNUPGHOME`.

        The `unset` makes your own `gpg` and `git` commands in this shell use your keyring again.
      </Tab>
      <Tab title="SSH">
        Create an Ed25519 key:

        ```bash
        PRIVATE_KEY_ID=$(tk --profile admin --message-format json ssh keys create \
          --name agent-git-signing | jq -r .privateKeyId)
        ```

        Let the agent sign with that key, and nothing else:

        ```bash
        tk --profile admin policy create --name agents-sign-ssh --effect allow \
          --consensus "approvers.any(user, user.id == '${AGENT_USER_ID}')" \
          --condition "activity.type == 'ACTIVITY_TYPE_SIGN_RAW_PAYLOAD_V2' && private_key.id == '${PRIVATE_KEY_ID}'"
        ```

        As the agent, register the key and add it to an allowed signers file, so that Git can verify its signatures:

        ```bash
        tk --profile agent ssh keys add --private-key-id "$PRIVATE_KEY_ID"
        SSH_PUBLIC_KEY=$(tk --profile agent ssh public-key --key "$PRIVATE_KEY_ID")
        mkdir -p ~/.config/git
        printf '%s %s\n' "jane+agent@example.com" "$SSH_PUBLIC_KEY" >> ~/.config/git/allowed_signers
        ```

        These commands do not use the policy. The test commit in step 4 is the first signature. If it fails with `unauthorized` (403), check the agent user ID and the private key ID in `agents-sign-ssh`.

        You can use this key for SSH in step 5 too. Then you need only one key and one policy.
      </Tab>
    </Tabs>
  </Step>

  <Step title="4. Point Git at tk for the agent only">
    This step uses the names `agent` and `tk-sign`. If you set up more than one agent on this machine, use the names in [Several agents on one machine](#several-agents-on-one-machine) from the start.

    Git starts `tk` with no `tk` flags, so a small wrapper selects the agent's profile:

    ```bash
    mkdir -p ~/.local/bin
    cat > ~/.local/bin/tk-sign <<'EOF'
    #!/bin/sh
    export PATH="$HOME/.local/bin:$PATH"
    export TK_PROFILE=agent
    exec tk "$@"
    EOF
    chmod 755 ~/.local/bin/tk-sign
    ```

    Do not use `git config --global`. That changes the signing setup for you too. Put the config in the agent runtime's environment. Git applies `GIT_CONFIG_KEY_n` and `GIT_CONFIG_VALUE_n` pairs above all config files, and only in processes that get them. These maps do not expand `$HOME` or `~`, so write full paths.

    The tabs show the pairs for GPG signing. For SSH signing, use the 7-pair block below the tabs.

    <Tabs>
      <Tab title="Claude Code">
        In `~/.claude/settings.json` (create the file if it does not exist). Replace `FINGERPRINT` with the value from step 3 (`echo "$FINGERPRINT"`), and replace `/Users/jane` with your home directory. If the file has an `env` object already, add these keys to it:

        ```json
        {
          "env": {
            "GIT_CONFIG_COUNT": "6",
            "GIT_CONFIG_KEY_0": "gpg.format",
            "GIT_CONFIG_VALUE_0": "openpgp",
            "GIT_CONFIG_KEY_1": "gpg.program",
            "GIT_CONFIG_VALUE_1": "/Users/jane/.local/bin/tk-sign",
            "GIT_CONFIG_KEY_2": "user.signingkey",
            "GIT_CONFIG_VALUE_2": "FINGERPRINT",
            "GIT_CONFIG_KEY_3": "commit.gpgsign",
            "GIT_CONFIG_VALUE_3": "true",
            "GIT_CONFIG_KEY_4": "user.name",
            "GIT_CONFIG_VALUE_4": "Jane Doe (agent)",
            "GIT_CONFIG_KEY_5": "user.email",
            "GIT_CONFIG_VALUE_5": "jane+agent@example.com",
            "GNUPGHOME": "/Users/jane/.config/turnkey/tk/gnupg"
          }
        }
        ```
      </Tab>
      <Tab title="Codex">
        In `~/.codex/config.toml`. Replace `FINGERPRINT` with the value from step 3 (`echo "$FINGERPRINT"`), and replace `/Users/jane` with your home directory:

        ```toml
        [shell_environment_policy.set]
        GIT_CONFIG_COUNT = "6"
        GIT_CONFIG_KEY_0 = "gpg.format"
        GIT_CONFIG_VALUE_0 = "openpgp"
        GIT_CONFIG_KEY_1 = "gpg.program"
        GIT_CONFIG_VALUE_1 = "/Users/jane/.local/bin/tk-sign"
        GIT_CONFIG_KEY_2 = "user.signingkey"
        GIT_CONFIG_VALUE_2 = "FINGERPRINT"
        GIT_CONFIG_KEY_3 = "commit.gpgsign"
        GIT_CONFIG_VALUE_3 = "true"
        GIT_CONFIG_KEY_4 = "user.name"
        GIT_CONFIG_VALUE_4 = "Jane Doe (agent)"
        GIT_CONFIG_KEY_5 = "user.email"
        GIT_CONFIG_VALUE_5 = "jane+agent@example.com"
        GNUPGHOME = "/Users/jane/.config/turnkey/tk/gnupg"

        [sandbox_workspace_write]
        network_access = true
        ```

        Each signature is a call to Turnkey. The `workspace-write` sandbox has no network access by default, so turn it on, or approve the escalation when Codex asks.
      </Tab>
      <Tab title="Only the agent uses this machine">
        If no person signs on this machine, use global config:

        ```bash
        git config --global gpg.format openpgp
        git config --global gpg.program ~/.local/bin/tk-sign
        git config --global user.signingkey "$FINGERPRINT"
        git config --global commit.gpgsign true
        ```
      </Tab>
    </Tabs>

    For SSH signing, use these 7 pairs in place of the GPG pairs, and do not set `GNUPGHOME`. For `user.signingkey`, write `key::` and then the output of `tk --profile agent ssh public-key --key "$PRIVATE_KEY_ID"`:

    ```json
    {
      "env": {
        "GIT_CONFIG_COUNT": "7",
        "GIT_CONFIG_KEY_0": "gpg.format",
        "GIT_CONFIG_VALUE_0": "ssh",
        "GIT_CONFIG_KEY_1": "gpg.ssh.program",
        "GIT_CONFIG_VALUE_1": "/Users/jane/.local/bin/tk-sign",
        "GIT_CONFIG_KEY_2": "user.signingkey",
        "GIT_CONFIG_VALUE_2": "key::ssh-ed25519 AAAA...",
        "GIT_CONFIG_KEY_3": "commit.gpgsign",
        "GIT_CONFIG_VALUE_3": "true",
        "GIT_CONFIG_KEY_4": "user.name",
        "GIT_CONFIG_VALUE_4": "Jane Doe (agent)",
        "GIT_CONFIG_KEY_5": "user.email",
        "GIT_CONFIG_VALUE_5": "jane+agent@example.com",
        "GIT_CONFIG_KEY_6": "gpg.ssh.allowedSignersFile",
        "GIT_CONFIG_VALUE_6": "/Users/jane/.config/git/allowed_signers"
      }
    }
    ```

    For Codex, use the same keys and values in the TOML table.

    Start a new agent session, and make a test commit in a Git repository in it. A new repository is enough, for example one from `git init`. You do not need a remote:

    ```bash
    git commit -S --allow-empty -m "test signing"
    git verify-commit HEAD
    ```

    To test without a new agent session, export the `env` values in a new shell, and run the same commands in it. For Claude Code:

    ```bash
    (eval "$(jq -r '.env | to_entries[] | "export \(.key)=\(.value|@sh)"' ~/.claude/settings.json)"
     git commit -S --allow-empty -m "test signing" && git verify-commit HEAD)
    ```

    For Codex:

    ```bash
    (eval "$(awk '/^\[/{s=($0=="[shell_environment_policy.set]")} s && /=/{k=$1; sub(/^[^=]*= */,""); print "export " k "=" $0}' ~/.codex/config.toml)"
     git commit -S --allow-empty -m "test signing" && git verify-commit HEAD)
    ```

    Run these in a Git repository.

    For SSH signing, `git verify-commit` in your own shell fails with `gpg.ssh.allowedSignersFile needs to be configured`, because only the agent's environment sets that file. To check an agent's commit from your own shell, run `git -c gpg.ssh.allowedSignersFile="$HOME/.config/git/allowed_signers" verify-commit HEAD`.
  </Step>

  <Step title="5. Push over SSH with a Turnkey key">
    Create an Ed25519 key and let the agent use it. If you chose SSH signing in step 3, you can use that key and its policy instead: set `SSH_KEY_ID` to `PRIVATE_KEY_ID` and go to the `ssh keys add` command.

    ```bash
    SSH_KEY_ID=$(tk --profile admin --message-format json ssh keys create \
      --name agent-ssh | jq -r .privateKeyId)
    echo "$SSH_KEY_ID"
    tk --profile admin policy create --name agents-ssh-auth --effect allow \
      --consensus "approvers.any(user, user.id == '${AGENT_USER_ID}')" \
      --condition "activity.type == 'ACTIVITY_TYPE_SIGN_RAW_PAYLOAD_V2' && private_key.id == '${SSH_KEY_ID}'"
    ```

    `ssh keys create` creates the key and also registers it. Make sure that `echo "$SSH_KEY_ID"` does not print an empty line or `null`. If the command fails after it created the key (for example with 429), do not run it again, because that makes a second key. Wait a minute. Get the ID with `tk --profile admin --message-format json activity list | jq -r '.data.items[].result.createPrivateKeysResultV2.privateKeys[]?.privateKeyId'`, and run `tk --profile admin ssh keys add --private-key-id "$SSH_KEY_ID"`.

    As the agent, register the key, save its public key, and start the SSH agent. If you set up several agents, do not run the last command in this block. Start the SSH agent with the command in [Several agents on one machine](#several-agents-on-one-machine). The allowed-hosts file limits the agent to the GitHub host keys. Compare the `ssh-keyscan` output with [GitHub's published fingerprints](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/githubs-ssh-key-fingerprints).

    ```bash
    tk --profile agent ssh keys add --private-key-id "$SSH_KEY_ID"
    tk --profile agent ssh public-key --key "$SSH_KEY_ID" > ~/.config/turnkey/agent-ssh.pub
    ssh-keyscan github.com > ~/.config/turnkey/ssh-allowed-hosts
    tk --profile agent ssh agent start --allowed-hosts-file ~/.config/turnkey/ssh-allowed-hosts
    ```

    Add the public key to the GitHub account that the agent pushes as, under **Settings > SSH and GPG keys > New SSH key**, with the key type **Authentication Key**.

    Then add `core.sshCommand` to the agent's environment from step 4 as the next pair, and increase `GIT_CONFIG_COUNT` by one. With GPG signing, this is pair 6 and the count is `7`, as in this example. With SSH signing, use `7` in place of `6` in both names, and the count is `8`:

    ```json
    "GIT_CONFIG_KEY_6": "core.sshCommand",
    "GIT_CONFIG_VALUE_6": "ssh -o IdentityAgent=~/.config/turnkey/ssh-agent.sock -o IdentitiesOnly=yes -o IdentityFile=~/.config/turnkey/agent-ssh.pub -o UserKnownHostsFile=~/.config/turnkey/ssh-allowed-hosts"
    ```

    For Codex, add the same key and value to the `[shell_environment_policy.set]` table, for example `GIT_CONFIG_KEY_6 = "core.sshCommand"`.

    `ssh` expands `~` in these options. `IdentitiesOnly` stops `ssh` from offering the keys in `~/.ssh`, so the agent can use only the Turnkey key. The allowed-hosts file limits the Turnkey SSH agent, but `ssh` does not read it for host trust. `UserKnownHostsFile` makes `ssh` use the same GitHub host keys, so the connection works on a machine where `ssh` has not connected to GitHub before.

    Test it from a new agent session, which gets `core.sshCommand`. The session that you used for setup does not have it. To test without a new session, run the commands in a subshell that exports the `env` values, as in step 4. For example:

    ```bash
    (eval "$(jq -r '.env | to_entries[] | "export \(.key)=\(.value|@sh)"' ~/.claude/settings.json)"
     git ls-remote git@github.com:OWNER/REPO.git)
    ```

    These commands test the SSH agent directly:

    ```bash
    ssh -o IdentityAgent=~/.config/turnkey/ssh-agent.sock -o IdentitiesOnly=yes \
      -o IdentityFile=~/.config/turnkey/agent-ssh.pub \
      -o UserKnownHostsFile=~/.config/turnkey/ssh-allowed-hosts -T git@github.com
    git ls-remote git@github.com:OWNER/REPO.git
    ```

    If the test works, `ssh` prints `Hi USERNAME! You've successfully authenticated, but GitHub does not provide shell access.` and exits with status 1. This status is correct, because GitHub gives no shell. `git ls-remote` prints the refs and exits with status 0.

    <Warning>
      `tk ssh agent` stops when you log out or restart. Start it again with the same `ssh agent start` command that you used above. If you set up several agents, start each one again with its own `--key`, `--socket`, and `--pid-file`, as in [Several agents on one machine](#several-agents-on-one-machine). A plain `tk ssh agent start` serves every registered key.
    </Warning>
  </Step>

  <Step title="6. Get Verified on GitHub">
    `git verify-commit` passes on your machine after step 4. For GitHub to show the commits as **Verified**, do these steps in a browser:

    1. Add the committer email (`jane+agent@example.com`) under **Settings > Emails**, and open the confirmation link that GitHub sends.
    2. Upload the signing public key under **Settings > SSH and GPG keys**. For GPG, add it as a **New GPG key**. For SSH signing, add it as a **New SSH key** with the key type **Signing Key**.

    To upload the GPG key with the GitHub CLI:

    ```bash
    gh auth refresh -s write:gpg_key,user:email
    tk --profile agent gpg keys export --key "$FINGERPRINT" > ./agent-signing-key.asc
    gh gpg-key add ./agent-signing-key.asc --title "agent signing (Turnkey)"
    ```

    Commits that you pushed before become Verified when both steps are complete.
  </Step>
</Steps>

### Optional: co-author trailer

To add `Co-authored-by: Turnkey <noreply@turnkey.com>` to each agent commit, add two more pairs to the agent's environment, and increase `GIT_CONFIG_COUNT` by two. Use the next two unused numbers. This example follows SSH signing and `core.sshCommand`:

```json
"GIT_CONFIG_COUNT": "10",
"GIT_CONFIG_KEY_8": "hook.turnkey-co-author.event",
"GIT_CONFIG_VALUE_8": "commit-msg",
"GIT_CONFIG_KEY_9": "hook.turnkey-co-author.command",
"GIT_CONFIG_VALUE_9": "/Users/jane/.local/bin/tk git co-author"
```

If a number is missing, Git stops with `missing config key GIT_CONFIG_KEY_n`.

This needs Git 2.54 or later. The `/usr/bin/git` on macOS is older. It ignores the hook and shows no error. Put a newer Git first on the agent's `PATH`.

## Several agents on one machine

Give each agent its own identity: its own Turnkey user, tk profile, keys, policies, wrapper, and SSH agent socket. Then each agent signs with its own key, its commits show its own name, and you can revoke one agent and keep the others.

Do steps 2 to 5 one time for each agent, with that agent's names. Use a separate shell for each agent, so that `AGENT_USER_ID`, `WALLET_ID`, `FINGERPRINT`, and `SSH_KEY_ID` do not overwrite each other. If your agent runs each command in a new shell, use one values file for each agent, such as `~/.config/turnkey/setup-claude.env` and `~/.config/turnkey/setup-codex.env`, in place of `setup.env`. Source only that agent's file in its commands. Do not use the names `agent` and `tk-sign` from the steps, because each agent would replace the files of the agent before it. In every command and config value, replace the profile and user `agent`, the OpenPGP user ID in `gpg keys create --user-id`, `user.name`, `user.email`, the wrapper path in `gpg.program`, the SSH key name, `agent-ssh.pub`, `ssh-agent.sock`, and the PID file. This table shows the names for Claude Code and Codex:

| | Claude Code | Codex |
| :--- | :--- | :--- |
| Turnkey user and tk profile (step 2) | `claude` | `codex` |
| Committer identity | `Jane Doe (claude) <jane+claude@example.com>` | `Jane Doe (codex) <jane+codex@example.com>` |
| Wallet and signing policy (step 3) | `git-signing-claude`, `agents-sign-gpg-claude` | `git-signing-codex`, `agents-sign-gpg-codex` |
| Wrapper (step 4) | `~/.local/bin/tk-sign-claude` | `~/.local/bin/tk-sign-codex` |
| Agent config (step 4) | The Claude Code tab | The Codex tab |
| SSH key and policy (step 5) | `claude-ssh`, `agents-ssh-auth-claude` | `codex-ssh`, `agents-ssh-auth-codex` |
| SSH public key file (step 5) | `~/.config/turnkey/claude-ssh.pub` | `~/.config/turnkey/codex-ssh.pub` |
| SSH agent socket (step 5) | `~/.config/turnkey/ssh-claude.sock` | `~/.config/turnkey/ssh-codex.sock` |
| SSH agent PID file (step 5) | `~/.config/turnkey/ssh-claude.pid` | `~/.config/turnkey/ssh-codex.pid` |

Do these one time only, not for each agent:

- The `agent` tag and the `agents-no-credentials` policy in step 2. They apply to all agents with the tag.
- The GnuPG home in step 3. It holds only public keys, so the agents can share it. Import each agent's public key into it.
- The allowed-hosts file in step 5 (`~/.config/turnkey/ssh-allowed-hosts`). Each agent's SSH agent can use it.

Each wrapper sets the profile of its agent. For Claude Code:

```bash
cat > ~/.local/bin/tk-sign-claude <<'EOF'
#!/bin/sh
export PATH="$HOME/.local/bin:$PATH"
export TK_PROFILE=claude
exec tk "$@"
EOF
chmod 755 ~/.local/bin/tk-sign-claude
```

All profiles under one `HOME` share one key registry. A plain `tk ssh agent start` serves every registered key, so each agent could use the keys of the others. In step 5, start one SSH agent for each identity. Give it its own socket and PID file, and let it serve only its own key:

```bash
CLAUDE_SSH_FINGERPRINT=$(ssh-keygen -lf ~/.config/turnkey/claude-ssh.pub | awk '{print $2}')
tk --profile claude ssh agent start --key "$CLAUDE_SSH_FINGERPRINT" \
  --socket ~/.config/turnkey/ssh-claude.sock --pid-file ~/.config/turnkey/ssh-claude.pid \
  --allowed-hosts-file ~/.config/turnkey/ssh-allowed-hosts
```

For Codex, use the same wrapper and command with `codex` in place of `claude`. In each agent's `core.sshCommand`, set `IdentityAgent` to that agent's socket and `IdentityFile` to its public key file. To stop or check one SSH agent, give `tk ssh agent stop` or `tk ssh agent status` the same `--socket` and `--pid-file`.

Make sure that each socket serves only its own key. This command must print exactly one key, and it must be the key in `claude-ssh.pub`:

```bash
SSH_AUTH_SOCK=~/.config/turnkey/ssh-claude.sock ssh-add -L
```

## Sign your own commits

You can use the same setup to sign your own commits with a Turnkey key, without an agent:

1. Do step 1 for your own user. You do not need step 2.
2. Do step 3 with your root profile (for example `admin`) in place of both `admin` and `agent`, and your own name and email in the key's user ID. If you are the only member of the root quorum, you do not need a signing policy. If not, create one that names your user.
3. Use the global config from step 4. It replaces your old `gpg.program` and `user.signingkey`. Also run `git config --global user.name "Jane Doe"` and `git config --global user.email jane@example.com` with your own name and email. Name the wrapper `~/.local/bin/tk-sign-me` in place of `tk-sign`, so that it does not replace the wrapper of an agent, and set its `TK_PROFILE` to your profile. For GPG, add `export GNUPGHOME="$HOME/.config/turnkey/tk/gnupg"` to the wrapper too, so that `git verify-commit` finds the public key in every shell. If you signed commits with a local GnuPG key before, import its public key into the Turnkey GnuPG home, so that `git verify-commit` can still check those commits. Then set its trust, as in step 3: `gpg --export OLD_FINGERPRINT | GNUPGHOME="$HOME/.config/turnkey/tk/gnupg" gpg --import` and `echo "OLD_FINGERPRINT:6:" | GNUPGHOME="$HOME/.config/turnkey/tk/gnupg" gpg --import-ownertrust`.
4. Do steps 5 and 6 with your own profile and email. In step 5, use your own names: the key `me-ssh`, the public key file `~/.config/turnkey/me-ssh.pub`, and the socket `~/.config/turnkey/ssh-me.sock`. Start the SSH agent so that it serves only your key:

   ```bash
   ME_SSH_FINGERPRINT=$(ssh-keygen -lf ~/.config/turnkey/me-ssh.pub | awk '{print $2}')
   tk --profile admin ssh agent start --key "$ME_SSH_FINGERPRINT" \
     --socket ~/.config/turnkey/ssh-me.sock --pid-file ~/.config/turnkey/ssh-me.pid \
     --allowed-hosts-file ~/.config/turnkey/ssh-allowed-hosts
   ```

   If you are the only member of the root quorum, do not create the `agents-ssh-auth` policy. If not, create it with your own user ID in place of `AGENT_USER_ID`. Then run this, with your home directory in place of `/Users/jane`:

   ```bash
   git config --global core.sshCommand "ssh -o IdentityAgent=/Users/jane/.config/turnkey/ssh-me.sock -o IdentitiesOnly=yes -o IdentityFile=/Users/jane/.config/turnkey/me-ssh.pub -o UserKnownHostsFile=/Users/jane/.config/turnkey/ssh-allowed-hosts"
   ```

   If your Git host is not GitHub, use its host keys in place of `ssh-keyscan github.com`.

You can then sign from any machine where your profile is set up, and you have no signing key file to copy or lose.

## Background agents

An agent in CI, a container, or a VM must not keep a long-lived credential. Use these setups:

- **Expiring session keys**: a provisioner registers an API key for the agent with an expiry and renews it. See [tk sessions](https://github.com/tkhq/tk/blob/main/docs/sessions.md) and the `provisioning-session-agent` skill.
- **Signing broker**: `tk gpg agent serve` holds the signing credential in a separate container. The agent's container gets only the socket and sets `TK_GPG_AGENT_SOCK`. See the `deploying-signing-broker` skill.
- **CI**: set `TURNKEY_ORGANIZATION_ID`, `TURNKEY_API_PUBLIC_KEY`, and `TURNKEY_API_PRIVATE_KEY` in the job, and set `gpg.program` to `tk`. See [tk authentication](https://github.com/tkhq/tk/blob/main/docs/authentication.md#ci).

### Sign from a sandbox through a socket

Keep the Turnkey credential out of the agent's sandbox. A broker outside the sandbox holds the credential and signs through a Unix socket. The sandbox gets only the socket and the public key. The agent can sign commits, but it cannot read the credential or use it for other Turnkey requests.

This example uses two OS users on one machine. The `broker` user holds the credential. The `agent` user is the sandbox. With containers or VMs, mount the socket directory and the public key into the sandbox, and give it nothing else from the broker. In production, give the broker an expiring session key. See the `deploying-signing-broker` skill.

1. Create the broker identity. As the `broker` OS user, install `tk` (step 1, without a profile) and create its profile. Write down the public key that it prints:

   ```bash
   tk --organization-id ORG_UUID profile create --profile-name broker
   ```

   As the operator, with your admin profile, set `PUBLIC_KEY` to the broker's public key. Create the broker user as in step 2, with `broker` as the user name, and keep the `agent` tag, so that the `agents-no-credentials` policy covers the broker too. Save its user ID as `AGENT_USER_ID`. Do not run the agent `tk login` and `whoami` commands from step 2. Then, as `broker`, run `tk login --profile-name broker` and `tk --profile broker whoami`. As the operator, do step 3 (GPG tab) up to `gpg keys create`. In the signing policy, use the broker's user ID. Do not import the key into GnuPG as the broker.

2. As root, create a group for the socket, add the agent to it, and create the directories. The `2` in `2750` makes the socket get the group of the directory:

   ```bash
   groupadd tk-sign
   usermod -aG tk-sign agent
   install -d -o broker -g tk-sign -m 2750 /run/tk-gpg-agent
   install -d -o broker -g broker -m 755 /opt/tk-gpg-public
   ```

3. As `broker`, set `WALLET_ID` and `FINGERPRINT` to the values from step 3. You set them in the operator's shell, so they are empty in the broker's shell. Then register the key, publish the public key, and start the broker. `serve` runs in the foreground. Run it under a supervisor, such as a systemd service, so that it starts again after a restart:

   ```bash
   tk --profile broker gpg keys add --wallet-id "$WALLET_ID" --key "$FINGERPRINT"
   tk --profile broker gpg keys export --key "$FINGERPRINT" > /opt/tk-gpg-public/signing-key.asc
   tk --profile broker gpg agent serve --key "$FINGERPRINT" \
     --socket /run/tk-gpg-agent/agent.sock --socket-mode 660 --non-interactive
   ```

4. As `agent`, install `tk` (step 1, without a profile), import the public key, and point Git at `tk`. Replace `FINGERPRINT` with the broker's key fingerprint:

   ```bash
   gpg --import /opt/tk-gpg-public/signing-key.asc
   echo "FINGERPRINT:6:" | gpg --import-ownertrust
   echo 'export TK_GPG_AGENT_SOCK=/run/tk-gpg-agent/agent.sock' >> ~/.profile
   git config --global gpg.format openpgp
   git config --global gpg.program "$HOME/.local/bin/tk"
   git config --global user.signingkey FINGERPRINT
   git config --global commit.gpgsign true
   git config --global user.name "Jane Doe (agent)"
   git config --global user.email jane+agent@example.com
   ```

   With `TK_GPG_AGENT_SOCK` set, `tk` sends each signature to the socket and needs no profile.

5. In a new login shell as `agent`, make a test commit in a Git repository, for example a new one from `git init`. Then make sure that the agent has no Turnkey credential: `tk whoami` must fail.

   ```bash
   git commit -S --allow-empty -m "test signing"
   git verify-commit HEAD
   tk whoami
   ```

   If the broker stops, signing fails. `tk` does not fall back to another credential. This setup signs commits only.

## Troubleshooting

| Problem | Cause and fix |
| :--- | :--- |
| `git commit -S` fails with `unauthorized` (403) | No policy lets this agent sign with this key. Check the agent's user ID in the consensus and the wallet or private key ID in the condition. Do not sign as root to work around it. |
| Signing waits or asks for approval | The policy needs an approval. Git waits for each signature, so use a policy that allows the agent to sign without approval. |
| `profile agent does not exist` | Git runs under a different `HOME` than the one with the profile. Add `export HOME=/path/to/agent/home` to the wrapper. |
| `no OpenPGP key in the registry matches signing key` | The key is not registered in Git's `HOME`. Run `tk --profile agent gpg keys add` there, or set `user.signingkey` to the exact fingerprint. |
| `git verify-commit` fails after a commit succeeds | For GPG, the agent's process does not have `GNUPGHOME`, or the ownertrust import was not done there. For SSH, the `allowed_signers` line does not pair the committer email with the key. |
| `gpg keys export`, `git commit -S`, or `ssh keys create` fails with 429 | The organization is over its rate limit. Wait a few minutes and try again. If `ssh keys create` failed after it created the key, do not run it again. See step 5. |
| `git push` fails with `agent refused operation` | Run `tk --profile agent ssh git-sign -Y sign -n git -f ~/.config/turnkey/agent-ssh.pub ./file.txt` to see the Turnkey error. A 429 means the organization is over its signing rate limit. |
| `gpg: can't connect to the gpg-agent: File name too long` | The socket path in `GNUPGHOME` is longer than the operating system permits (about 104 characters on macOS). Use a shorter `GNUPGHOME`, such as `~/.tk-gnupg`, in step 3 and step 4. |
| `ssh` says `Host key verification failed` | `ssh` does not trust the GitHub host key. Add `-o UserKnownHostsFile=~/.config/turnkey/ssh-allowed-hosts` as in step 5. |
| `ssh` says `invalid format` for `agent-ssh.pub`, or `tk ssh agent status` says `ssh-agent is not running` | The SSH agent stopped. Then `ssh` tries to read the public key file as a private key. Start the agent again. Some agent sandboxes stop background processes when a command ends. In that case, start the agent in the same command as `ssh` or `git`. |
| Commits are signed, but GitHub shows **Unverified** | The committer email is not confirmed on the GitHub account, or the key's user ID does not contain that email. Do step 6. |
