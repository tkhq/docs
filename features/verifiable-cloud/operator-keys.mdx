Every [operator](/features/verifiable-cloud/overview#operators) in a [manifest set or share set](/features/verifiable-cloud/manifest-sets-and-share-sets) is identified by a pair of P-256 public keys: one for signing manifest approvals and one for encryption, used to receive and re-encrypt Quorum Key shares. The private half of that pair can live in one of three places. This page describes each option so you can pick the right custody model for each operator.

## Compare the options

| | Local key file | Turnkey-hosted | YubiKey |
| :--- | :--- | :--- | :--- |
| Private key lives in | A JSON file on the operator's machine | Two wallet accounts in your Turnkey organization | PIV slots on a hardware token |
| Who controls it | You. Turnkey only ever sees the public keys | Your organization, through Turnkey's user, API key, and [policy](/features/policies/overview) model | You. Turnkey only ever sees the public keys |
| Where signing and decryption happen | On the operator's machine | Inside Turnkey's enclaves, via Turnkey activities | On the YubiKey, after a PIN and a touch |
| Created by | `tvc login` | `tvc operator create` | `ykman` on the device, then registered with `tvc` |
| Registered with Turnkey | When an operator set is created with `newOperators` | By the [`create_tvc_operator`](/api-reference/activities/create-tvc-operator) activity | When an operator set is created with `newOperators` |
| `keySource` in the API | `EXTERNAL_KEY` | `ORG_WALLET_ACCOUNT` | `EXTERNAL_KEY` |
| Can act in CI | Yes, with a seed file | Yes, with API key env vars | No, needs a physical touch |
| Best for | Development and prototypes | Automated pipelines, and share sets whose members shouldn't hold key material directly | Production manifest and share set members |

The kinds can be mixed freely within a set. A production app might use a YubiKey for each human reviewer in the manifest set and hosted operators for a CI pipeline and the share set.

The [`list_tvc_operators`](/api-reference/queries/list-tvc-operators) query reports each operator's `keySource`. Operators created before the field existed have no `keySource`.

## Local key file

`tvc login` generates a 32-byte master seed on your machine. Both the signing key and the encryption key are derived from that seed following the [QOS key set](https://github.com/tkhq/qos/blob/main/src/qos_p256/SPEC.md) specification. The seed is written as JSON to:

```
~/.config/turnkey/orgs/<alias>/operator.json
```

The seed never leaves the file unless you move it. Turnkey learns only the public keys, which the CLI auto-populates into the `newOperators` field when you run `tvc app init`, or which you paste into the dashboard when creating an app there.

**Back it up.** A lost local key means a lost operator. If that operator was needed to meet a threshold, you'll need to create a new operator set and a new app. `tvc login` offers to back the key up during onboarding, and you can do it any time:

```bash
tvc keys backup-operator-key --output <PATH>
```

Treat the backup like any other private key: store it encrypted, off the machine that uses it.

**Approve manifests.** With the organization active, the CLI reads the key from the file automatically:

```bash
tvc deploy approve \
  --deploy-id <DEPLOYMENT_UUID> \
  --operator-id <OPERATOR_UUID>
```

To sign from a pipeline or from a machine that hasn't run `tvc login`, pass the seed explicitly with `--operator-seed-path <FILE>` (a file containing the raw hex seed) or `--operator-seed <HEX>`. The two flags are mutually exclusive. Add `--skip-post` to produce an approval offline and post it later.

**Hold Quorum Key shares.** Local operators can be share set members too, but the share lifecycle runs on your machine rather than through Turnkey:

1. `tvc keys generate-local-quorum-key` generates a Quorum Key, splits it with Shamir's Secret Sharing, and encrypts each share to an operator's encryption key.
2. When an enclave boots, `tvc keys re-encrypt-local-share` verifies the enclave's attestation and manifest approvals, then re-encrypts your share to the enclave's Ephemeral Key.
3. `tvc deploy post-share` submits the re-encrypted share.

Each step accepts the same `--operator-seed` and `--operator-seed-path` flags as `deploy approve`. Run `tvc keys init-local-quorum-key` to generate a template configuration for step 1.

## Turnkey-hosted

A hosted operator's keys are two P-256 wallet accounts in your Turnkey organization. `tvc operator create` calls the [`create_tvc_operator`](/api-reference/activities/create-tvc-operator) activity, which creates a wallet named `tvc-wallet` (or reuses one you pass with `--wallet-id`) and derives two accounts under a base path. The default base path is `m/5527107'/0'/0'`, where `5527107` is the ASCII bytes of `TVC`. Turnkey appends `/0` for the encryption account and `/1` for the signing account.

```bash
tvc operator create --name <OPERATOR_NAME>
```

The activity returns the operator ID, the wallet ID, and both public keys. The CLI saves them to the active organization's local profile so later commands can find the operator by ID. To create more than one hosted operator in the same wallet, give each a distinct `--account-path`.

**Who controls the key.** The private keys never leave Turnkey's enclaves, and they are never returned to the CLI. Every use of a hosted operator is a Turnkey activity submitted with your API key, so it is subject to the same controls as any other activity in your organization: the submitting user's permissions, [policies](/features/policies/overview), consensus requirements, and the activity log. Hosted operators are a good fit when you want a team, rather than an individual's laptop, to control who can approve a manifest or release a share.

<Note>
A hosted operator is only as strong as the credentials allowed to use it. Scope the API keys and users that can sign with the operator's wallet accounts, and consider a policy that requires consensus for `ACTIVITY_TYPE_SIGN_RAW_PAYLOAD` and `ACTIVITY_TYPE_RE_ENCRYPT_TVC_QUORUM_KEY_SHARE` on production operators.
</Note>

**Approve manifests.** The same command as a local operator. The CLI recognizes the operator ID as a hosted operator and signs the approval through the [`sign_raw_payload`](/api-reference/activities/sign-raw-payload) activity instead of a local key:

```bash
tvc deploy approve \
  --deploy-id <DEPLOYMENT_UUID> \
  --operator-id <OPERATOR_UUID>
```

Offline approval with `--skip-post` is not available for hosted operators, since signing requires the API.

**Hold Quorum Key shares.** Hosted operators have a shorter share lifecycle because Turnkey holds the encrypted shares:

1. `tvc keys create-quorum-key --threshold <N> --operator-ids <IDS>` creates the Quorum Key inside Turnkey's enclaves with one share encrypted to each hosted operator.
2. `tvc deploy provision --deploy-id <ID> --operator-id <ID>` verifies the enclave's attestation and approvals, then calls the [`re_encrypt_tvc_quorum_key_share`](/api-reference/activities/re-encrypt-tvc-quorum-key-share) activity to re-encrypt that operator's share to the enclave's Ephemeral Key.

The [manifest sets and share sets](/features/verifiable-cloud/manifest-sets-and-share-sets#worked-example) page walks through a full hosted setup.
