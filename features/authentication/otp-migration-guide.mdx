sidebarTitle: "OTP migration guide"
description: "Migrate legacy OTP authentication, email authentication, and email recovery to encrypted OTP verification and client-bound sessions."
---

Turnkey's current email and SMS OTP flows encrypt each OTP attempt before it leaves the client. The client encrypts the code and a session public key to a Turnkey enclave target key. After successful verification, the resulting verification token is bound to the client public key, so an application server cannot read the OTP or use the token to log in or sign up without the matching client private key.

This guide is for integrations that use legacy OTP activities, SDK methods that send `otpCode` in plaintext, or legacy email authentication and recovery flows that deliver encrypted credential bundles. New integrations should use the current flow documented in [Email auth & recovery](/features/authentication/email) and [SMS authentication](/features/authentication/sms).

If your integration calls `initOtpAuth` followed by `otpAuth`, start with [Migrating from legacy OTP Auth](#migrating-from-legacy-otp-auth). That flow changes both the activity sequence and how the client receives and uses credentials.

If your integration uses `emailAuth` or `initUserEmailRecovery` followed by `recoverUser`, start with [Migrating from legacy email authentication and recovery](#migrating-from-legacy-email-authentication-and-recovery).

<Warning>
  Migrate each OTP attempt as a unit. Do not start an attempt with a legacy
  `INIT_OTP`, `INIT_OTP_V2`, or `INIT_OTP_AUTH*` activity and finish it with the updated `VERIFY_OTP_V2` or
  `OTP_LOGIN_V2` activities. The encryption bundle, verification token, and
  client key belong to the same attempt and are not interchangeable with the
  legacy flow.
</Warning>

## What changed

| Stage    | Legacy SDK activity                                     | Current SDK activity                       | Required change                                                                                                                                     |
| -------- | ------------------------------------------------------- | ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Initiate | `ACTIVITY_TYPE_INIT_OTP` or `ACTIVITY_TYPE_INIT_OTP_V2` | `ACTIVITY_TYPE_INIT_OTP_V3`                | Keep the returned `otpEncryptionTargetBundle` with the `otpId` until verification.                                                                  |
| Verify   | `ACTIVITY_TYPE_VERIFY_OTP`                              | `ACTIVITY_TYPE_VERIFY_OTP_V2`              | Replace plaintext `otpCode` and `publicKey` with an `encryptedOtpBundle`.                                                                           |
| Log in   | `ACTIVITY_TYPE_OTP_LOGIN`                               | `ACTIVITY_TYPE_OTP_LOGIN_V2`               | Include a `clientSignature` made by the key bound during verification.                                                                              |
| Sign up  | `ACTIVITY_TYPE_CREATE_SUB_ORGANIZATION_V7`              | `ACTIVITY_TYPE_CREATE_SUB_ORGANIZATION_V8` | Include a `clientSignature` when the verification token is bound to a public key. Version 8 and later do not accept legacy OTP verification tokens. |

<Note>
  `ACTIVITY_TYPE_CREATE_SUB_ORGANIZATION_V7` is transitional: it accepts both
  legacy verification tokens and the enclave-issued tokens returned by
  `VERIFY_OTP_V2`. `ACTIVITY_TYPE_CREATE_SUB_ORGANIZATION_V8` accepts only
  enclave-issued tokens. During a staged rollout, legacy attempts must remain on
  V7; updated attempts can use V7 or V8.
</Note>

The updated verification flow is:

1. `INIT_OTP_V3` returns `otpId` and `otpEncryptionTargetBundle`.
2. The client generates or selects a P-256 key pair.
3. The client uses `encryptOtpCodeToBundle` to encrypt the OTP code and public key with `otpEncryptionTargetBundle`.
4. `VERIFY_OTP_V2` accepts the encrypted bundle and returns a verification token bound to the client public key.
5. The client signs the login or signup payload with the same private key.
6. `OTP_LOGIN_V2` or the sub-organization creation flow validates the verification token and client signature.

See [OTP login flow](/security/enclave-secure-channels#otp-login-flow) for the protocol diagram and security properties.

## Migrating from legacy OTP Auth

This section applies to any integration that calls `initOtpAuth` and `otpAuth`, regardless of SDK. These methods are exposed through `@turnkey/http`, `apiClient()` in `@turnkey/sdk-server`, the browser SDK's `passkeyClient` / `iframeClient` / `walletClient` / `indexedDbClient`, and the `httpClient` exposed by Core and Wallet Kit. The built-in OTP helpers in Wallet Kit and Core don't use the legacy flow, but direct calls such as `useTurnkey().httpClient.otpAuth(...)` still require migration. To check whether you're affected, search your code for `initOtpAuth` or `otpAuth(`.

The legacy flow used two activities: one to send the code, and one to verify it and return a credential. The replacement flow splits verification and login into separate activities:

| Stage          | Legacy activity                                 | Replacement activity          | SDK method change         |
| -------------- | ----------------------------------------------- | ----------------------------- | ------------------------- |
| Send code      | `ACTIVITY_TYPE_INIT_OTP_AUTH`, `_V2`, or `_V3`  | `ACTIVITY_TYPE_INIT_OTP_V3`   | `initOtpAuth` → `initOtp` |
| Verify code    | Part of `ACTIVITY_TYPE_OTP_AUTH`                | `ACTIVITY_TYPE_VERIFY_OTP_V2` | `otpAuth` → `verifyOtp`   |
| Get credential | Part of `ACTIVITY_TYPE_OTP_AUTH`                | `ACTIVITY_TYPE_OTP_LOGIN_V2`  | `otpAuth` → `otpLogin`    |

All four legacy activities are deprecated.

<Warning>
  `INIT_OTP_AUTH_V3` is part of the legacy family; it is not the same activity
  as `INIT_OTP_V3`. Upgrading an SDK without replacing calls to `initOtpAuth`
  and `otpAuth` does not migrate this flow.
</Warning>

### Replace initialization, verification, and login

These steps assume your backend holds a parent-organization API key, which stays on the backend. If you submit OTP activities with sub-organization credentials instead, use that sub-organization ID for every step and skip step 5; see [Sub-organization initiated OTP](/features/authentication/email#sub-organization-initiated-otp).

1. **Before you deploy: update policies.** In the parent organization, permit the three replacement activities for the non-root API user that submits them, preserving existing user and organization restrictions. A root API user satisfying a root quorum threshold of one does not need these additional allow policies. See [Update policies before deploying](#update-policies-before-deploying).
2. **Backend: replace `initOtpAuth` with `initOtp`.** Submit `ACTIVITY_TYPE_INIT_OTP_V3` under the parent organization with the contact, `otpType` (`OTP_TYPE_EMAIL` or `OTP_TYPE_SMS`), and required `appName`. Return `otpId` and `otpEncryptionTargetBundle` to the client.
   - If you use `INIT_OTP_AUTH` or `INIT_OTP_AUTH_V2`, move `appName` out of `emailCustomization` into the top-level `appName` field. `INIT_OTP_V3` requires it, and its `emailCustomization` no longer accepts `appName`. See [Breaking change: `appName` required](/features/authentication/email#breaking-change-appname-required).
   - If you rely on the organization's default email template, register it for `ACTIVITY_TYPE_INIT_OTP`. Default templates registered for `ACTIVITY_TYPE_INIT_OTP_AUTH` are not selected automatically by the new flow. An existing template passed explicitly through `emailCustomization.templateId` can still be selected. Review its content for compatibility with the new flow.
   - Review your other email and SMS customization parameters against the new activity rather than copying the legacy request unchanged.
3. **Client: encrypt the code.** Generate or select a P-256 key pair. Use `encryptOtpCodeToBundle(otpCode, otpEncryptionTargetBundle, publicKey)` to encrypt the code and public key, and send only the resulting `encryptedOtpBundle` to your backend. The private key stays on the client.
4. **Backend: verify with `verifyOtp`.** Submit `ACTIVITY_TYPE_VERIFY_OTP_V2` with `otpId` and `encryptedOtpBundle`, using the same organization ID as initialization. Return the `verificationToken` to the client; it is bound to the client key used in the encrypted bundle.
5. **Backend: resolve the user's sub-organization.** After verification, look up the sub-organization for the contact, for example with `getSubOrgIds` filtered by `EMAIL` or `PHONE_NUMBER`. In the legacy flow you resolved the sub-organization before initialization, because `INIT_OTP_AUTH` is submitted to it. Move that lookup here, after the code is verified.
6. **Client: sign the login message.** Build the message with `getClientSignatureMessageForLogin` and sign it with the private key bound during verification. The message covers the token ID and the session public key; do not sign an arbitrary JSON representation of the token.
7. **Backend: replace `otpAuth` with `otpLogin`.** Submit `ACTIVITY_TYPE_OTP_LOGIN_V2` to the user's sub-organization with `verificationToken`, the session `publicKey`, and `clientSignature`.
8. **Client: store and use the session.** Use the returned `session` with the private key matching the session `publicKey` you passed to `OTP_LOGIN_V2`, following your SDK's session handling. Remove the legacy credential-bundle decryption and import step. See [Credential handling changes](#credential-handling-changes).

```ts title="Before (legacy OTP Auth)"
// Backend: INIT_OTP_AUTH is submitted to the user's sub-organization,
// so the sub-organization must be resolved first.
const { otpId } = await turnkey.apiClient().initOtpAuth({
  organizationId: subOrgId,
  otpType: "OTP_TYPE_EMAIL",
  contact: email,
  appName: "Example App",
});

// Backend: the client sends the plaintext code and a target public key.
const { credentialBundle } = await turnkey.apiClient().otpAuth({
  organizationId: subOrgId,
  otpId,
  otpCode,
  targetPublicKey,
});

// Client: decrypt credentialBundle and import the API key.
```

The following excerpts show the replacement flow in execution order, across separate client and backend contexts. They assume `turnkey` is an initialized `Turnkey` instance from `@turnkey/sdk-server`, configured with the parent organization's ID and API key on the backend. The client uses `@turnkey/react-wallet-kit`. Application request handlers, React state, and error handling are omitted; keep the returned values as state for the same OTP attempt.

**Backend: initialize and return the OTP ID and encryption bundle to the client.**

```ts title="Backend: initialize"
const { otpId, otpEncryptionTargetBundle } = await turnkey.apiClient().initOtp({
  otpType: "OTP_TYPE_EMAIL",
  contact: email,
  appName: "Example App",
});
```

**Client: create a key and encrypt the code.** Import the helpers below and obtain the key and session methods inside a React component or custom hook under `TurnkeyProvider`:

```ts title="Client: helper setup"
import { encryptOtpCodeToBundle } from "@turnkey/crypto";
import {
  getClientSignatureMessageForLogin,
  useTurnkey,
} from "@turnkey/react-wallet-kit";

// Inside your React component or custom hook:
const { createApiKeyPair, signWithApiKey, storeSession } = useTurnkey();
```

```ts title="Client: encrypt (async event handler)"
// Create a fresh key for this attempt and retain publicKey in component state.
// Wallet Kit stores the private key on the client.
const publicKey = await createApiKeyPair();
const encryptedOtpBundle = await encryptOtpCodeToBundle(
  otpCode,
  otpEncryptionTargetBundle,
  publicKey,
);
```

Send `otpId` and `encryptedOtpBundle` to the backend. The plaintext code and private key stay on the client.

**Backend: verify, then resolve the user's sub-organization.** Return the verification token and sub-organization ID to the client.

```ts title="Backend: verify and resolve"
// Use the same parent organization as initialization.
const { verificationToken } = await turnkey.apiClient().verifyOtp({
  otpId,
  encryptedOtpBundle,
});

const { organizationIds } = await turnkey.apiClient().getSubOrgIds({
  filterType: "EMAIL",
  filterValue: email,
});
const subOrgId = organizationIds[0]; // If none is found, sign up instead.
```

**Client: sign with the same key used for verification.** Here, `signWithApiKey` is the Wallet Kit hook method obtained above; it is not the function of the same name exported by `@turnkey/sdk-server`.

```ts title="Client: sign (async event handler)"
const { message } = getClientSignatureMessageForLogin({ verificationToken });
const signature = await signWithApiKey({ message, publicKey });
const clientSignature = {
  scheme: "CLIENT_SIGNATURE_SCHEME_API_P256" as const,
  publicKey,
  message,
  signature,
};
```

Send `verificationToken`, `publicKey`, and `clientSignature` to the backend to complete login for the resolved sub-organization.

**Backend: log in and return the session to the client.**

```ts title="Backend: log in"
const { session } = await turnkey.apiClient().otpLogin({
  organizationId: subOrgId,
  verificationToken,
  publicKey,
  clientSignature,
});
```

**Client: store the session using Wallet Kit.**

```ts title="Client: store session (async event handler)"
await storeSession({ sessionToken: session });
```

The [`otp-auth/with-backend` example](https://github.com/tkhq/sdk/tree/main/examples/authentication/otp-auth/with-backend) shows the complete client and backend split, including key creation and new-user signup. Despite its name, this example uses the replacement flow.

### Credential handling changes

| Legacy `OTP_AUTH` | Replacement `OTP_LOGIN_V2` |
| --- | --- |
| Takes `otpCode` and a `targetPublicKey` used to encrypt a generated credential. | Takes a `verificationToken`, session `publicKey`, and `clientSignature` after encrypted OTP verification. |
| Returns `userId`, `apiKeyId`, and `credentialBundle`. The client decrypts the bundle to obtain its signing credential. | Returns `session`, a session JWT. The client keeps the signing private key it generated; the JWT does not contain a replacement private key. If you used `userId` from the `OTP_AUTH` result, read it from the session JWT's `user_id` claim. |
| `expirationSeconds` sets the generated OTP Auth API key's lifetime. | `expirationSeconds` on login sets the session lifetime. Initialization and verification have separate expiration settings for the OTP and verification token. |
| `invalidateExisting` invalidates previous OTP Auth API keys. | `invalidateExisting` invalidates all of the user's existing login sessions, including sessions created through OAuth or passkey login, not only OTP sessions. It does not revoke legacy OTP Auth API keys. |
| Accepts an optional `apiKeyName`. | Has no `apiKeyName` parameter. |

Allow legacy OTP Auth credentials to expire, or revoke them separately if your application requires an immediate cutoff. Credential checks belong in a policy's `consensus` expression, not its `condition`. A check such as `credentials.any(c, c.type == 'CREDENTIAL_TYPE_OTP_AUTH_KEY_P256')` will not match requests authenticated with the new login sessions. For those requests, use `credentials.any(c, c.type == 'CREDENTIAL_TYPE_LOGIN')`, preserving any other restrictions in your consensus expression.

Requests authenticated with an attested stamp using the verification token and its bound client key expose `CREDENTIAL_TYPE_EMAIL` or `CREDENTIAL_TYPE_PHONE` in policy evaluation, depending on the verification method. These are policy-expression values for attested stamps, not members of the public `CredentialType` enum or stored API-key types; see [Attested-stamp credential types](/features/users/credentials#attested-stamp-credential-types). They are distinct from `CREDENTIAL_TYPE_LOGIN` session requests. Update the relevant credential checks before you roll out, then test session expiration, invalidation, and at least one wallet operation with the new session. A successful login alone does not show that later operations have the permissions your application expects.

## Migrating from legacy email authentication and recovery

This section applies to integrations using:

- `ACTIVITY_TYPE_EMAIL_AUTH`, `ACTIVITY_TYPE_EMAIL_AUTH_V2`, or `ACTIVITY_TYPE_EMAIL_AUTH_V3`
- `ACTIVITY_TYPE_INIT_USER_EMAIL_RECOVERY` or `ACTIVITY_TYPE_INIT_USER_EMAIL_RECOVERY_V2`, followed by `ACTIVITY_TYPE_RECOVER_USER`

These legacy flows deliver an encrypted credential bundle through email. The replacement uses encrypted email OTP verification and a session bound to a client-held key.

Email remains available for authentication and recovery through the encrypted OTP flow. This migration changes the activity sequence, email experience, credential handling, and permissions. Upgrading the SDK alone does not replace existing calls to the legacy methods.

### Choose the flow that matches your integration

| Existing use case | Replacement |
| --- | --- |
| Sign in using an emailed credential bundle | `INIT_OTP_V3` → `VERIFY_OTP_V2` → `OTP_LOGIN_V2` |
| Recover access by enrolling a replacement passkey | Encrypted email OTP → recovery session → `CREATE_AUTHENTICATORS_V2` → sign in with the new passkey |

Recovery includes authenticator enrollment. Completing OTP login alone does not replace the entire legacy `INIT_USER_EMAIL_RECOVERY` → `RECOVER_USER` flow.

### Before you deploy

- Upgrade the relevant SDK packages to the versions listed in [Upgrade the SDKs](#upgrade-the-sdks).
- Confirm that `FEATURE_NAME_OTP_EMAIL_AUTH` is enabled for the target sub-organization. The legacy email-authentication and email-recovery feature settings do not substitute for this setting. See [Email feature configuration](/features/authentication/email#implementation-in-organizations) and [Set organization feature](/api-reference/activities/set-organization-feature).
- Update activity permissions to allow `ACTIVITY_TYPE_INIT_OTP_V3`, `ACTIVITY_TYPE_VERIFY_OTP_V2`, and `ACTIVITY_TYPE_OTP_LOGIN_V2` for the users submitting those requests. For recovery, also ensure the recovering user can submit `ACTIVITY_TYPE_CREATE_AUTHENTICATORS_V2` with the recovery session. Preserve existing user, organization, and operation restrictions; see [Update policies before deploying](#update-policies-before-deploying).
- Review credential-type checks in policy `consensus` expressions. Legacy checks for `CREDENTIAL_TYPE_EMAIL_AUTH_KEY_P256` or `CREDENTIAL_TYPE_RECOVER_USER_KEY_P256` do not match requests stamped with the new `CREDENTIAL_TYPE_LOGIN` sessions. When updating these checks, retain the recovery flow's restrictions on permitted operations and users; matching a login session alone does not restrict it to recovery.
- Review your email templates and callback UI. The replacement sends an OTP to verify, rather than a recovery or authentication credential bundle to import.
- Review existing MFA policy conditions as well as which user stamps each request. Conditions that name legacy activity kinds or versions must be updated for the replacement flow.

Adding MFA is not a prerequisite for this migration. Existing applicable MFA policies must still be satisfied. For additional recovery protections, see [MFA Recovery](/features/authentication/mfa/enforcement-and-recovery).

### Preserve existing MFA enforcement

Update MFA conditions that match legacy activities. For example, `activity.kind == 'EMAIL_AUTH'` does not match `OTP_LOGIN`, and `activity.kind == 'RECOVER_USER'` does not match `CREATE_AUTHENTICATORS`. Review conditions using exact `activity.type` values too. Apply the intended authentication requirements to the replacement login and authenticator-enrollment activities, preserving existing user and operation restrictions. During a staged rollout, keep the legacy activities covered until all clients have migrated.

Before implementing login, decide which user will stamp the request. MFA policies apply to the user whose credential stamps the request.

A login stamped with a parent-organization API key evaluates that parent user's MFA policies. It does not evaluate the target sub-organization user's MFA policies merely because the login is for that user.

The `clientSignature` parameter and the request's authentication stamp serve different purposes. Including `clientSignature` in a backend-stamped login does not make the request end-user-stamped. If authentication or recovery relies on the end user's MFA policies, have the client submit login with an **attested stamp** using the verification token and its bound client key. See [Obtaining the attested stamp](/features/authentication/mfa/satisfying-mfa#obtaining-the-attested-stamp).

Handle any required authentication challenges before using the returned session. The resulting session may also encounter MFA requirements when enrolling an authenticator. See [MFA evaluation](/features/authentication/mfa/overview#mfa-is-evaluated-for-the-user-who-stamped) for details.

### Replace email authentication

The following sequence assumes initialization and verification use a parent-organization backend.

1. **Initialize email OTP.** Replace `emailAuth` with `initOtp`, submitting `ACTIVITY_TYPE_INIT_OTP_V3` under the parent organization. Set `otpType` to `OTP_TYPE_EMAIL`, provide the user's email as `contact`, and include the required top-level `appName`. Return both `otpId` and `otpEncryptionTargetBundle` to the client.
2. **Encrypt the OTP on the client.** Generate or select a client P-256 key pair. Use `encryptOtpCodeToBundle` to encrypt the OTP and public key with the returned target bundle. Keep the private key and plaintext OTP on the client.
3. **Verify the encrypted submission.** Submit `ACTIVITY_TYPE_VERIFY_OTP_V2` with `otpId` and `encryptedOtpBundle`, using the same organization ID as initialization. Retain the returned `verificationToken` with the client key used for this attempt.
4. **Resolve the existing account and complete login.** Identify the user's sub-organization after verification. Submit `ACTIVITY_TYPE_OTP_LOGIN_V2` to that sub-organization with the verification token, session public key, and required client signature, using the request stamp chosen in [Preserve existing MFA enforcement](#preserve-existing-mfa-enforcement).
5. **Use the returned session.** Store the session using your SDK's session handling. Remove the legacy credential-bundle decryption and import step. The signing private key remains on the client.

If no existing account is found, handle that result explicitly. Account recovery must not silently create a new account.

For encrypted bundle creation and client-signature examples, see [Migrating from legacy OTP Auth](#migrating-from-legacy-otp-auth).

### Replace email recovery

Before enabling recovery, create a short-lived session profile in the parent organization with scope limited to authenticator enrollment. For example, submit [Create session profile](/api-reference/activities/create-session-profile) with these parameters and retain the returned `sessionProfileId`:

```json
{
  "sessionProfileName": "recovery-authenticator-only",
  "scope": "activity.kind == 'CREATE_AUTHENTICATORS'",
  "expirationSeconds": "600"
}
```

A session profile limits the session's permissions; it does not automatically require MFA.

Email OTP is an authentication method, not a separate recovery-only credential. The profile restricts requests stamped with the issued session; it does not restrict other uses of the verification token and its bound client key. Those remain usable for [attested requests while the token is valid](/features/authentication/mfa/satisfying-mfa#while-an-activity-is-held). If your application intends email to grant only recovery access, enforce that requirement through the applicable authorization and MFA policies, and validate every supported login path. Selecting the recovery profile in the UI alone does not enforce it. Test requests that omit or change `sessionProfileId`, as well as direct attested requests for operations outside recovery.

For each recovery attempt, follow the initialization, encryption, and verification steps above, then complete login directly into the recovery session:

1. **Resolve the existing account and obtain a recovery session.** Submit `ACTIVITY_TYPE_OTP_LOGIN_V2` to the user's sub-organization with the verification token, session public key, required client signature, and recovery `sessionProfileId`. Use the request stamp chosen in [Preserve existing MFA enforcement](#preserve-existing-mfa-enforcement) and complete any MFA challenges. This login creates the recovery session. Omitting `sessionProfileId` creates a default read/write session with no scope restrictions.
2. **Enroll a replacement passkey.** Complete WebAuthn registration on the client, then submit `ACTIVITY_TYPE_CREATE_AUTHENTICATORS_V2` for the recovering user, stamped with the recovery session. This replaces the legacy `recoverUser` step.
3. **Sign in with the new passkey.** Confirm that the new authenticator works before considering recovery complete. Handle removal of lost or compromised authenticators according to your application's recovery policy.

At the SDK level, replace `recoverUser` with `createAuthenticators` and wrap the registration result in the `authenticators` array:

```ts title="Before: legacy recovery credential"
await legacyRecoveryClient.recoverUser({
  organizationId: subOrgId,
  userId,
  authenticator,
});
```

```ts title="After: recovery session"
await recoverySessionClient.createAuthenticators({
  organizationId: subOrgId,
  userId,
  authenticators: [authenticator],
});
```

These excerpts assume initialized low-level SDK clients: `legacyRecoveryClient` uses the imported legacy recovery credential, and `recoverySessionClient` uses the newly issued recovery session and its client-held signing key. Set `subOrgId` and `userId` to the existing account being recovered. The `authenticator` object contains `authenticatorName`, `challenge`, and `attestation` from the new WebAuthn registration; see [Create authenticators](/api-reference/activities/create-authenticators) for the request fields.

The new passkey is an ordinary authenticator and does not inherit the recovery session's scope or expiration. Subsequent requests authenticated with it remain subject to the user's applicable authorization and MFA policies.

See [Session Profiles](/features/authentication/sessions/session-profiles) for session restrictions and [MFA Recovery](/features/authentication/mfa/enforcement-and-recovery) for the recommended additional-factor recovery pattern.

### Review session invalidation and legacy credentials

The meaning of `invalidateExisting` changes when you replace email authentication with OTP login:

| Legacy `EMAIL_AUTH` | Replacement `OTP_LOGIN_V2` |
| --- | --- |
| Invalidates previously generated Email Auth API keys. | Invalidates all other login sessions for the user, including sessions created through OAuth or passkey login. It does not revoke legacy Email Auth API keys. |

Review this behavior before carrying `invalidateExisting: true` into the new login flow. Account for outstanding legacy credentials separately: allow them to expire or revoke them according to your application's policy. Creating a new session does not itself revoke credentials issued by the old flow.

### Verify the migration

Before removing the legacy flow, confirm that:

- An existing user can complete email authentication or recovery.
- Recovery enrolls a working replacement authenticator in the existing account.
- MFA conditions cover the replacement activities and still trigger the intended challenges. During rollout, verify the legacy flow remains covered too.
- Any recovery-session restrictions prevent operations outside the intended scope.
- If email is intended only for recovery, omitting or changing `sessionProfileId`, or submitting direct attested requests with the verification token, does not bypass those restrictions.
- The replacement passkey is subject to the intended authorization and MFA policies when used for normal login and subsequent operations.
- Session expiration and invalidation behave as expected, including the effect on sessions created through other login methods.
- Subsequent wallet operations work with the normal login session; recovery sessions remain limited to authenticator enrollment.
- Legacy method calls and credential-bundle handling have been removed.

    ```ts
    const otpId = await initOtp({
      otpType: OtpType.Email,
      contact: "user@example.com",
    });

    // After
    const { otpId, otpEncryptionTargetBundle } = await initOtp({
      otpType: OtpType.Email,
      contact: "user@example.com",
    });
    ```

    Pass the bundle to `verifyOtp`. The SDK encrypts the OTP code and public key before calling Turnkey:

    ```ts
    const { verificationToken } = await verifyOtp({
      otpId,
      otpCode,
      otpEncryptionTargetBundle,
    });
    ```

    `verifyOtp` no longer accepts `contact` or `otpType`, and it no longer returns `subOrganizationId`. Use `completeOtp` to perform verification plus account lookup and login/signup. For Auth Proxy integrations that perform account lookup separately, call `httpClient.proxyGetAccount` after verification. For backend-driven integrations, use the `getSubOrgIds` lookup shown in [Migrating from legacy OTP Auth](#migrating-from-legacy-otp-auth).

    `loginWithOtp` and `signUpWithOtp` no longer accept a separate `publicKey`. They reuse the key bound during `verifyOtp` and generate the required client signature automatically.

    ```ts
    await loginWithOtp({
      verificationToken,
      invalidateExisting: true,
    });
    ```

  </Tab>

  <Tab title="Legacy React SDK">
    `@turnkey/sdk-react` is the legacy React SDK. For new projects, use `@turnkey/react-wallet-kit`; see [Migrating from `@turnkey/sdk-react`](/solutions/embedded-wallets/integration-guide/react/migrating-sdk-react).

    If you are maintaining an `@turnkey/sdk-react` integration, the `OtpVerification` component now requires the encryption target bundle returned by `sendOtp`:

    ```ts
    const { otpId, otpEncryptionTargetBundle } = await server.sendOtp({
      appName: "Example App",
      otpType: OtpType.Sms,
      contact: phoneInput,
      customSmsMessage: "Your OTP is {{.OtpCode}}",
      userIdentifier: publicKey,
    });
    ```

    ```tsx
    <OtpVerification
      type={type}
      contact={contact}
      otpId={otpId}
      otpEncryptionTargetBundle={otpEncryptionTargetBundle}
      onValidateSuccess={handleValidateSuccess}
      onResendCode={handleResendCode}
    />
    ```

    The component handles creation of the encrypted OTP bundle. Make sure a resend replaces both `otpId` and `otpEncryptionTargetBundle`; never combine values from separate attempts.

  </Tab>

  <Tab title="Server and low-level clients">
    Legacy `@turnkey/sdk-react-native` integrations also follow this section. That package re-exports the low-level `@turnkey/http` client and does not automate OTP bundle creation or client signatures. For new React Native integrations, use [React Native Wallet Kit](/solutions/embedded-wallets/integration-guide/react-native/overview).

    `sendOtp` and `initOtp` now return an encryption target bundle. Persist it only for the lifetime of the OTP attempt and return it to the client that will verify the code.

    ```ts
    const { otpId, otpEncryptionTargetBundle } = await server.sendOtp({
      // ...
    });
    ```

    Replace the plaintext `otpCode` field with a bundle created on the client:

    ```ts
    import { encryptOtpCodeToBundle } from "@turnkey/crypto";

    const encryptedOtpBundle = await encryptOtpCodeToBundle(
      otpCode,
      otpEncryptionTargetBundle,
      publicKey,
    );

    const { verificationToken } = await server.verifyOtp({
      otpId,
      encryptedOtpBundle,
      sessionLengthSeconds, // Verification token lifetime, not session length.
    });
    ```

    The private key matching `publicKey` must stay on the client. Use it to sign the login or signup message, then send the resulting `clientSignature` to the backend:

    ```ts
    await server.otpLogin({
      suborgID,
      verificationToken,
      publicKey,
      clientSignature,
      sessionLengthSeconds,
    });
    ```

    `server.otpLogin` does not accept `invalidateExisting`. If you need it, call `turnkey.apiClient().otpLogin` directly.

    The [`otp-auth/with-backend`](https://github.com/tkhq/sdk/tree/main/examples/authentication/otp-auth/with-backend) example shows the full split between client-side encryption and signing and server-side Turnkey API calls.

## Update policies before deploying

If a policy checks exact activity versions, update it before the new SDKs begin submitting activities. At minimum, review policies that name:

- `ACTIVITY_TYPE_INIT_OTP` or `ACTIVITY_TYPE_INIT_OTP_V2`
- `ACTIVITY_TYPE_VERIFY_OTP`
- `ACTIVITY_TYPE_OTP_LOGIN`
- `ACTIVITY_TYPE_INIT_OTP_AUTH`, `ACTIVITY_TYPE_INIT_OTP_AUTH_V2`, or `ACTIVITY_TYPE_INIT_OTP_AUTH_V3`
- `ACTIVITY_TYPE_OTP_AUTH`
- `ACTIVITY_TYPE_EMAIL_AUTH`, `ACTIVITY_TYPE_EMAIL_AUTH_V2`, or `ACTIVITY_TYPE_EMAIL_AUTH_V3`
- `ACTIVITY_TYPE_INIT_USER_EMAIL_RECOVERY`, `ACTIVITY_TYPE_INIT_USER_EMAIL_RECOVERY_V2`, or `ACTIVITY_TYPE_RECOVER_USER`
- `ACTIVITY_TYPE_CREATE_SUB_ORGANIZATION_V7`

### Policies for legacy OTP Auth

The replacement flow changes activity kinds as well as versions: a condition permitting `INIT_OTP_AUTH` or `OTP_AUTH` will not match `INIT_OTP`, `VERIFY_OTP`, or `OTP_LOGIN`. For the parent-initiated flow described above, create the following policies in the parent organization for the non-root backend API user performing existing-user login. Parent-organization policies are evaluated even though `OTP_LOGIN_V2` targets the user's sub-organization. A root API user satisfying a root quorum threshold of one does not need these additional allow policies. If you initiate the flow with sub-organization credentials instead, configure the policies in that sub-organization. Replace the user ID and preserve any additional restrictions from your existing policies.

**During rollout**, allow both flows until every client uses the replacement flow:

```json
{
  "effect": "EFFECT_ALLOW",
  "consensus": "approvers.any(user, user.id == '<YOUR_API_USER_ID>')",
  "condition": "activity.kind in ['INIT_OTP_AUTH', 'OTP_AUTH', 'INIT_OTP', 'VERIFY_OTP', 'OTP_LOGIN']"
}
```

**After rollout**, permit only the replacement activity versions:

```json
{
  "effect": "EFFECT_ALLOW",
  "consensus": "approvers.any(user, user.id == '<YOUR_API_USER_ID>')",
  "condition": "activity.type in ['ACTIVITY_TYPE_INIT_OTP_V3', 'ACTIVITY_TYPE_VERIFY_OTP_V2', 'ACTIVITY_TYPE_OTP_LOGIN_V2']"
}
```

These examples do not grant signup permission. Add sub-organization creation permissions only if your integration also supports signup.

### Policies for other OTP flows

During a staged rollout, exact-type policies must allow both legacy and updated versions until all clients and servers use the new flow. This does not make the activity versions interchangeable within an OTP attempt. While both versions are in use, `activity.kind` covers every version of each activity:

```json
{
  "effect": "EFFECT_ALLOW",
  "consensus": "approvers.any(user, user.id == '<YOUR_API_USER_ID>')",
  "condition": "activity.kind in ['INIT_OTP', 'VERIFY_OTP', 'OTP_LOGIN', 'CREATE_SUB_ORGANIZATION']"
}
```

<Note>
  `CREATE_SUB_ORGANIZATION` covers every version of sub-organization creation,
  not only OTP signup. Preserve any existing restrictions on who may create a
  sub-organization and which parameters they may submit.
</Note>

A kind-based policy also continues to permit the legacy plaintext activities, such as `VERIFY_OTP`. After all clients have migrated, replace it with exact activity types.

## Rollout checklist

- Update policies before deploying updated SDKs.
- Upgrade the frontend and backend Turnkey packages together.
- Store `otpId`, `otpEncryptionTargetBundle`, and the client key as state for one OTP attempt.
- On resend, replace all attempt state rather than reusing an old bundle or key.
- Test email and SMS separately if your application supports both.
- Test both an existing-user login and a new-user signup.
- Confirm that OTP codes are sent to your backend only as `encryptedOtpBundle`.
- For legacy OTP Auth integrations, confirm there are no remaining `initOtpAuth` or `otpAuth` callers, and that clients use sessions instead of decrypting `credentialBundle` responses.
- Test session expiration, invalidation, and a wallet operation with the new session. Account for any legacy OTP Auth credentials that have not yet expired or been revoked.
- After all clients have migrated, remove legacy activity versions from exact-version policies, and replace kind-based OTP policies with exact types so the plaintext flows are no longer permitted.

For the complete set of SDK breaking changes shipped with this migration, see [tkhq/sdk#1250](https://github.com/tkhq/sdk/pull/1250).
